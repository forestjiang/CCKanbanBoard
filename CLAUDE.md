# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-file demo/training Kanban board for "UOB IT PMO" — an internal IT project management tool. The entire application (markup, styles, logic) lives in one file: `index.html`. There is no build, lint, or test tooling, no package.json, and no server.

## Running it

Open `index.html` directly in a browser (double-click, or `file://` path). No install step, no dev server, no compilation. There is no test suite or linter configured — verify changes by opening the file in a browser and exercising the UI manually (drag-and-drop between columns, the "Move ▸" select fallback, add/delete task, filters).

## Hard constraints (do not violate these when editing)

- **Vanilla HTML/CSS/JS only** — no frameworks (React, Vue, jQuery, Tailwind), no build step, no bundler, no npm packages, no external CDN scripts/fonts/images. Everything must stay inline in `index.html`.
- **No persistence of any kind** — no `localStorage`, `sessionStorage`, `IndexedDB`, cookies, or backend database. Board state is an in-memory JS object only and intentionally resets on page refresh (there's a visible note in the header saying so — keep it if state ever becomes non-trivial to lose).
- **FormSubmit is the only network call** — the app posts to a FormSubmit AJAX endpoint (`formsubmit.co`) purely to email-notify on new task creation. It must never block or break the board UI on failure (wrapped in try/catch, shown as a non-blocking toast).
- Never hardcode a real personal/user email into `FORMSUBMIT_ENDPOINT` — keep it a placeholder (`YOUR_EMAIL@example.com`) since this file may be shared or committed.
- Do not use UOB's real logo/trademarks — the header uses a neutral text wordmark and a corporate-blue palette only.
- All seed data (task titles, CVE numbers, assignee names, etc.) is fabricated placeholder content for demo purposes, not real records — keep new seed data equally fictional and clearly non-attributable to real people/systems.

## Architecture (single file: `index.html`)

The script is an IIFE with one `state` object as the single source of truth:

```js
state = {
  tasks: [],                                   // all task objects
  filters: { project, assignee, priority },    // active filter bar values
  confirmDeleteId: null,                       // which card (if any) shows inline delete confirm
  idCounter: 0                                 // last-used numeric id, for UOB-ITPM-#### generation
}
```

Everything on screen is derived from `state` via `renderBoard()` → `renderCard()` / `renderSummary()`. There is no direct DOM mutation of card content outside this render path — mutations (`moveTask`, `deleteTask`, `addTask`) update `state` and then call `renderBoard()`.

Key structural points to know before editing:

- **Columns are static DOM** (`Backlog` / `In Progress` / `Blocked` / `Done`, hardcoded in the HTML). Only each `.column-body[data-status]`'s `innerHTML` and the column badge count are replaced on render — this is why drag/drop and click/change listeners are attached once via **event delegation** on `#board` (and per-column-body for `dragover`/`dragleave`/`drop`) rather than re-attached per card on every render.
- **Two ways to move a task between columns**: native HTML5 drag-and-drop (`dragstart`/`dragover`/`drop`) and a keyboard-accessible "Move ▸" `<select>` on each card — both call the same `moveTask(id, newStatus)`.
- **Delete uses an inline confirm, not `confirm()`**: clicking the × sets `state.confirmDeleteId` and re-renders that card with a Yes/No row instead of opening a native dialog.
- **All user-supplied strings are passed through `escapeHtml()`** before being interpolated into template-string HTML in `renderCard()`/`renderSummary()`. Preserve this on any new field that gets rendered.
- **Add Task flow is optimistic**: `addTask()` pushes to `state.tasks` and re-renders immediately; `notifyNewTask()` (the FormSubmit call) fires afterward and only affects the toast shown, never the board state.
- Task IDs are generated by `makeTaskId(n)` as `UOB-ITPM-####` (zero-padded), driven off the same `state.idCounter` used by the seed data — new tasks continue the sequence rather than restarting it.

## FormSubmit activation note

FormSubmit requires a one-time confirmation: the first submission to a given address triggers a confirmation email, and no submissions deliver until that link is clicked. This is a property of the third-party service, not a bug in the app.
